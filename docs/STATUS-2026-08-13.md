# copse implementation status and gap analysis

Date: 2026-08-13

## Executive summary

copse 0.1.0 is a reliable Git worktree lifecycle manager, not yet the complete
parallel-agent framework described by its design. The implemented slice covers
deterministic branch/worktree naming, creation, carried ignored files, status,
safe removal, and basic diagnostics. The missing product layers are repository
onboarding, agent-aware launch and hooks, verification and merge closure,
repository protection, and lightweight coordination between parallel features.

Against the complete target, the repository was approximately 35% complete at
the start of this work. The worktree lifecycle itself was approximately 80%
complete; the framework and enforcement layers were mostly design only.

## Completion outcome

The ordered gap-closing plan has now been completed on branch
`feat/complete-framework`. copse 0.2.0 implements the intended framework end
to end: safe onboarding, Git/Codex/Claude hooks, agent-aware worktree launch,
shared ownership and dependency coordination, local/CI verification, guarded
GitHub merge and cleanup, ruleset provisioning, packaging acceptance, and
self-hosted project wiring.

The final acceptance run exercises 109 unit and real-Git integration cases,
syntax-checks every source/test module, packs and installs the npm artifact in
a temporary consumer, invokes its CLI, and runs the complete `copse verify`
path. The measured source coverage is above 95% by line, with CI running the
suite across Node 20, 22, and 24. Nested carried-directory symlinks and
concurrent coordination updates were added during final hardening, closing the
remaining known safety gaps found in review.

## What was already strong

- `copse new` fetched the configured base branch, created a branch and sibling
  worktree, copied declared ignored files/directories, and optionally ran an
  install command.
- `copse list` showed worktrees, naming drift, dirty/unpushed state, and pull
  request state.
- `copse drop` refused destructive removal and rescued carried paths held only
  by the worktree.
- Path traversal, leaf symlink, intermediate symlink, missing-upstream, unknown
  Git status, bare repository, and prefix-collision cases had explicit tests.
- The baseline suite passed in a real temporary Git repository and declared 80
  individual tests across four test files.

## Gaps that prevent the intended experience

### No automatic repository onboarding

There was no `copse init`, so a new or existing repository could not reconcile
configuration, Git hooks, CI, Codex hooks, Claude Code hooks, or shared agent
instructions. `doctor` checked only carried paths and naming drift.

### No agent-aware entry point

`copse new` printed a `cd` command but could not move the parent shell and did
not launch an agent. A dedicated launcher is required to resolve or create the
worktree and start Claude Code, Codex, or an arbitrary command with that
worktree as its working directory.

### No merge closure

There was no `copse land`; pushing, creating a pull request, checking CI,
merging, and cleaning up remained manual. `drop` deliberately retained the
branch and did not merge anything.

### Isolation without coordination

Worktrees prevent concurrent sessions from overwriting the same uncommitted
files, but they do not prevent duplicate task ownership, expose dependencies,
coordinate merge order, or diagnose shared local resources. A lightweight,
versioned feature registry is sufficient; a scheduler is not required.

### Distribution and dogfooding were incomplete

The package metadata and executable existed, but the package was not published
and copse did not use its own full wiring. Acceptance requires a complete
init-to-land lifecycle in a consuming repository and copse's own repository.

## Completion order

1. Repository onboarding, generated forwards, hooks, and expanded doctor.
2. Agent-aware `start` plus feature ownership and dependency state.
3. Shared `verify`, merge-oriented `land`, and GitHub `protect`.
4. CI hardening, documentation, packaging checks, and end-to-end acceptance.

This report is the baseline against which the completion specification and
implementation plan are verified.
